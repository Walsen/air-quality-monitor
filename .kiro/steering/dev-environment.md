# Development environment

Every project in this workspace gets a reproducible, declarative development
environment before any feature work starts. Two contributors on different
machines, and CI on a clean runner, must resolve the same toolchain from files
committed to the repository — never from whatever happens to be installed on
the host.

## Toolchain

| Tool | Owns | Where it is declared |
|------|------|----------------------|
| **devbox** | The whole non-Python toolchain, pinned per project | host prerequisite; manages `devbox.json` |
| **direnv** | Activating that toolchain on `cd`, deactivating on exit | host prerequisite; reads `.envrc` |
| **uv** | Python dependency resolution, locking, and the project virtual environment | `devbox.json` package; owns `pyproject.toml` + `uv.lock` |
| **python** | The interpreter version | `devbox.json` package |
| **just** | The documented command surface — test, run, lint, synth, backfill | `devbox.json` package; recipes in `Justfile` |
| **jq** | JSON inspection in recipes and scripts | `devbox.json` package |
| **yq** | YAML inspection in recipes and scripts | `devbox.json` package |
| **awscli2** | Ad hoc AWS inspection and deploy-adjacent commands | `devbox.json` package |
| **gh** | Pull requests, releases, CI runs from the terminal | `devbox.json` package |

### Host prerequisites versus project packages

**devbox and direnv are host prerequisites, not project packages.** Devbox
cannot install itself, and direnv has to be on the shell *before* you enter the
directory or there is nothing to trigger activation. Install direnv once with
`devbox global add direnv` so it is available across every project, and hook it
into your shell. Everything else in the table above belongs in the project's own
`devbox.json` so it is versioned with the code that needs it.

## Required files at the repository root

- **`devbox.json`** — the package list. Created with `devbox init`, populated
  with `devbox add <pkg>@<version>`.
- **`devbox.lock`** — committed. This is what makes the environment
  reproducible; without it the resolved versions can drift.
- **`.envrc`** — generated by `devbox generate direnv`, containing
  `eval "$(devbox generate direnv --print-envrc)"`. Committed, then trusted
  locally with `direnv allow`.
- **`Justfile`** — every command a contributor or CI stage needs to run.
- **`.gitignore`** — must exclude `.devbox/`, `.venv/`, and any generated
  credential tree.

## Pinning

**Pin every devbox package to an exact version.** Devbox defaults an omitted
version to `@latest`, which pins nothing and lets the toolchain drift between
machines and between commits. This is the same rule the engineering practices
apply to application dependencies, extended to the tools that build them:

```json
{
  "packages": [
    "python@<exact>",
    "uv@<exact>",
    "just@<exact>",
    "jq@<exact>",
    "yq-go@<exact>",
    "awscli2@<exact>",
    "gh@<exact>"
  ]
}
```

Resolve each `<exact>` with `devbox search <pkg>` and commit `devbox.lock`
alongside. Upgrade deliberately, as its own reviewable commit, never as a side
effect of someone else's checkout.

Note the package name: in the Nix package set, `yq` is the Python wrapper around
jq while `yq-go` is the Go implementation most recipes assume. Name the one you
actually want rather than taking the default.

## Python: devbox provides the interpreter, uv owns the dependencies

Do not install Python packages with the interpreter devbox provides. A
Nix-installed interpreter cannot write to its own store path, and installing
globally would defeat the per-project isolation devbox exists to give.

- `devbox.json` pins the **interpreter version**.
- `uv` creates and manages the project virtual environment, resolves
  dependencies, and writes `uv.lock`.
- Each service keeps its own `pyproject.toml`, consistent with the monorepo rule
  that a service owns its own manifest.
- `uv.lock` is committed. It is what satisfies the exact-version requirement the
  specs place on direct dependencies.

## just is the command surface

Every command named in a spec or a README is a `just` recipe, so there is one
documented way to run each thing and CI and a contributor invoke the same code
path. At minimum: `just test`, `just lint`, `just typecheck`, `just up` for the
local Compose stack, and — where the project has infrastructure — `just synth`.

A spec that requires "the single documented test command" is satisfied by a
recipe, not by a shell snippet pasted into a README.

## Relationship to Docker Compose

These are complementary and should not be confused. Devbox provides the
**host toolchain** — interpreter, CLIs, task runner. Docker Compose provides
**runtime dependencies** the application talks to over the network, such as a
local MQTT broker. A contributor runs `devbox shell` (or lets direnv do it) and
then `just up`; the two are not alternatives.

## Constraints this must not break

- **Offline test guarantee.** Having `awscli2` and `gh` on the PATH must not
  make any test depend on them. Suites that are required to pass with no cloud
  credentials and no network beyond localhost must keep doing so with the full
  toolchain present.
- **No secrets in committed files.** Environment variables that carry secrets
  are supplied at runtime. `.envrc` may export non-sensitive configuration and
  must never contain a key, token, or credential path holding real material.
  Use a git-ignored `.env.local` or the platform secret store instead.

## Bootstrapping a new project

1. `devbox init`, then `devbox add` each tool at an exact version.
2. `devbox generate direnv` and `direnv allow`.
3. `uv init` per service, then `uv add` its dependencies; commit `uv.lock`.
4. Write the `Justfile` recipes the specs and README refer to.
5. Add `.devbox/`, `.venv/`, and any generated credential tree to `.gitignore`.
6. Commit `devbox.json`, `devbox.lock`, `.envrc`, `Justfile`, and every
   `uv.lock` together, so the environment is reproducible from that commit on.
